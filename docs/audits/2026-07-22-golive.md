## Cleanup Plan

### Safe (no history rewrite)
- None required — branches, tags, and releases are already clean and policy-compliant. (Stale local tracking refs already pruned as part of this audit; no server-side action needed.)

### Rewrite (needs force-push — user approval required per operation, none executed)
- **Author-email rewrite** via `git filter-repo --mailmap` across all 234 commits, replacing:
  - `root@<internal-host>` → `newblacc@users.noreply.github.com` (2 commits — internal hostname, highest priority)
  - `celestinmax@gmail.com` → `newblacc@users.noreply.github.com` (1 commit)
  - `new.blacc@proton.me` → `newblacc@users.noreply.github.com` (~35 commits)
  - **Cost, stated honestly**: this rewrites every commit SHA in the repo, requires a force-push to `main`, breaks any existing local clones/forks (including this one), and invalidates every SHA already referenced in `docs/audits/*.md`, prior PR descriptions, and the CHANGELOG's own historical entries. This is the single most disruptive fix in this report. Recommend only if the personal-email/hostname exposure is judged worse than the rewrite cost — the user's call, not a default action.
- **Personal home-path history purge** (finding surfaced in Stage 3, recorded here since it's the same rewrite bucket — scope corrected after a full-history content scan, see Stage 3's Operational note): `/Users/<redacted>/...` appears in historical revisions of 6 file paths (`HANDOFF.md`, `.vscode/mcp.json`, `docs/audits/2026-07-20-job-ready.md`, `docs/codex_config_bug_report.md`, `docs/handoff-2026-04-06.md`, `docs/PLAN-production-ready.md`) across 26 unique commits — all already fixed/clean in the current tracked tree, but permanently present in history. Because the leak moved across renamed paths, `git filter-repo --replace-text` (a literal string/regex redaction of the path itself, e.g. `/Users/<redacted>/ ==> /Users/<redacted>/`) is more robust here than path-based removal — it catches the string regardless of which filename it lived under at the time. This is a *different* operation from the mailmap rewrite above — it redacts content, not authorship — but would typically be run in the same session since both require the same force-push and both invalidate the same SHAs. A single combined history rewrite is more efficient than two separate force-pushes.
